# Carmelita / ChatGPT read-channel parity

This sprint starts from `main` after PR38. The shared read registry is the source of executable contracts. Carmelita's authenticated query endpoint, deterministic chat reads and the authenticated MCP endpoint call the same definitions. Existing conversation and context tool names/scopes remain compatible. Adapter coverage means implementation exists; it does **not** establish provider availability, an individual connection, or completed live acceptance.

## Side-effect findings and corrections

- Public offer search/detail previously reached `providerDb()`, which prepares its schema. The common catalog now selects only eight public columns of published offers, validates their contract, and never creates schema, providers or offers. Both legacy public adapters preserve their DTOs. New personal reads label demos, publication source and unestablished fulfillment availability. A read-only diagnostic on 2026-10-01 found the existing provider/catalog tables empty in QA and production; this is not proof of an operative third-party service.
- Requesting conversation history in the web chat now presents five bounded previews from the shared latest-80-message result. The API/MCP result and normal chat reload preserve their existing data contract. The web reply does not store a recursive full copy of earlier history replies.
- The legacy conversation getter inserted a conversation and welcome message. Shared conversation readers use owner-bound SELECT only and return an empty result when none exists. Existing history selects the newest 80 messages and returns that bounded window in chronological order; a conversation longer than 80 no longer hides its latest replies after reload. Chat message persistence remains in the chat adapter. The SQL fixture covers a long conversation and a newer foreign-owner message without changing any records.
- Memory list and DeFindex/Soroswap status routes invoked runtime `CREATE TABLE/INDEX` helpers. Shared reads avoid route lifecycle/schema helpers and call pure SELECT/provider adapters. Database/schema preparation remains an existing separate responsibility; this sprint adds no migration.
- An owner-scoped workspace remount now discards profile, travel results/errors/selections, conversation, draft and child panel state together when the Privy identity changes. Displayed profile email is also explicitly owner-matched. Travel searches abort on owner/sign-out/new-search changes and recheck cancellation after token acquisition and JSON parsing, so a late prior-owner result cannot populate the current workspace. Deferred-response fixtures verify cancellation; visible authenticated owner-switch acceptance remains a separate gate.
- NFT reads use the official Avalanche Data API chain/address and NFT collection/token routes instead of nonexistent `/networks/fuji/collections` or `/holders` routes. Collection metadata never supplies invented global totals. Holder percentages use only known ERC721 owners in the first page of at most 50 tokens, exposing sample size, denominator and pagination. Provenance uses an independent Routescan ERC721-transfer mirror; missing mirror data or disagreements remain explicit. NFT floor remains unavailable.
- Aave Fuji readers use the current Pool and distinct ProtocolDataProvider from the [official Aave address book](https://github.com/bgd-labs/aave-address-book/blob/main/src/ts/AaveV3Fuji.ts), with its current reserve ABI and exact rate/balance strings for JSON transport. Configuration calls target the DataProvider, reserve data target the Pool and personal balances target returned aTokens. The separate transaction-preparation constants and financial lifecycle remain unchanged. Direct provider diagnostics and ABI fixtures do not establish authenticated web/ChatGPT acceptance.
- DeFindex's GET uses the shared position reader and a bounded, owner-bound public history projection without schema preparation. Infrastructure GET shares the same safe public metadata projection as its authenticated query. CCTP's fee/readiness POST branches share their readers; its plan branch remains in the separate financial lifecycle.
- Legacy wallet panels returned persistence/provider identifier fields. Shared personal output projects only approved registration metadata, state and explorer links. A registration state is not a balance or activation guarantee.
- Existing Notion OAuth retrieval can refresh the **existing** credential and its expiry metadata. Refresh now preserves the exact stored scope grant: omitted scopes retain it, equivalent case-sensitive sets retain its original order/duplicates, and additions, reductions, substitutions, explicit empty scopes or invalid scope values require visible reconnection before new credentials are persisted or used. Tokens remain server-only. `tests/notion-refresh-scopes.test.ts` checks owner isolation, grant preservation, rejected refreshes without credential changes, and the visible connection prerequisite with no workspace business read.
- Some CCTP reads conflated failed Stellar lookup with a negative trustline result. Shared readiness preserves null for unknown chain reads, distinguishing unavailable, absent registration and verified negative state.
- Provider payloads and metadata are external data. No remote instructions are executed. Error responses return bounded public codes, never arbitrary upstream body/token strings.
- Discovery readers whitelist their local public error codes; a private string resembling an error identifier is suppressed. A contradictory Fuji RPC chain identity invalidates its token reading rather than attributing another network's balance to Fuji.
- Catalog connection requirements are explicit individual authorization prerequisites. Server API keys and wallet records remain separate requirements and never imply a missing user connection. Continuation links are validated HTTPS origins suitable for ChatGPT, without embedded credentials.
- Existing PAT verification now reads the prepared credential table directly; schema preparation remains in credential issuance/administration. Revocation, expiration, last-used tracking and rate limiting remain enforced. OAuth verification/subject resolution are read-only and never create an identity link.

## Evidence-derived query acceptance

`app/queries/acceptance-manifest.json` and `acceptance-evidence.json` are versioned and initially empty. Installed adapters alone do not certify a live integration. Registry discovery and the capability catalog use the same pure evaluator in `acceptance.ts`; neither hardcodes permanent pending status nor treats a fixture/HTTP diagnostic as an actual user consultation.

An accepted entry references two sanitized observations, one from Carmelita and one from ChatGPT. Each records its real served commit, deployment, UTC date, environment and a neutral tester alias; it contains no Privy identity, email, wallet address, token, cookie or arbitrary provider text. Both observations must report an operational result and approved owner/authorization/isolation, unchanged wallet/permission, semantic and read-only controls. ChatGPT additionally requires discovery of the current tool. The same alias correlates the already verified owner across channels; it does not replace the private identity comparison.

The manifest binds canonical observation digests, the query's exact input/scope/data-scope contract fingerprint, and a current execution fingerprint. A prior observation keeps its original commit and date; it can apply to a later commit only when its contract and execution fingerprint actually match. Acceptance of a changed history reader or capability metadata is not inherited from an unchanged market query.

`acceptance-source-fingerprint.ts` is a build/test helper, never a deployed filesystem reader. It follows local runtime imports and fingerprints compiled TypeScript with the dependency/compiler configuration in six conservative groups, including the public commerce catalog. Business execution excludes unrelated acceptance/catalog metadata; personal history remains part of the personal group. `acceptance-runtime.json` stores the checked results for the deployed evaluator. When a group changes, regenerate those fingerprints and revalidate that group's affected real evidence; refreshing hashes alone does not establish acceptance. Runtime configuration, provider data, private wallet references and OAuth expiration have independent controls and are not proved by source equivalence.

`tests/query-acceptance.test.ts` runs automatically in `npm test`. It rejects unsupported/duplicate manifest entries, digest or fingerprint drift, a single channel, synthetic observations, missing controls, future dates and outcomes such as unavailable or connection-required. Strict observation fields reject credential and private-identity additions. The committed-artifact test permits future real accepted entries, but only through the same evaluator and CI checks.

`provider: verified` and its dated `verification.kind: historical` describe that recorded operational acceptance. They never assert permanent provider health or that every user has connected. Individual connection requirements stay separate; current execution results still report missing connections, provider failures, partial results and stale data. A known unavailable source cannot be certified as an available integration. The initial empty artifacts leave every query pending, with no claim of actual cabscrypto or ChatGPT acceptance.

Lint passed for the full candidate; the additional catalog, contracts, permissions and bounded-history group passed 53 targeted tests. The two skipped cases do not provide external acceptance.

Catalog response limits and optional null fields were corrected from measured current responses, without inventing metrics. These direct server checks are not authenticated web or ChatGPT acceptance. Aave Fuji, LFJ, Travala and Soroswap remain distinct provider/configuration acceptance entries; Soroswap health alone does not establish quote availability.

The authenticated diagnostic on isolated QA candidate `4c5f2c6` passed on 2026-10-01. All 42 installed read tools were discovered with their strict contracts; insufficient scopes and an attempted foreign-owner selector were rejected for every tool, while the original context/conversation scopes remained distinct. The synthetic principal's personal reads stayed empty and created no user or wallet. Temporary diagnostic credentials were revoked and removed. That MCP diagnostic also returned operational market quotes/search, chain comparison, Avalanche documentation/tool discovery, AVAX Skills, Dexalot pairs and a non-firm quote, Gamma markets, Avalanche yields and the MPP catalog. Missing personal connections and wallet prerequisites remained explicit; unavailable NFT floor data remained null. This evidence applies to the synthetic HTTP diagnostic and candidate `4c5f2c6`. It does **not** establish cabscrypto acceptance, actual ChatGPT discovery or consultation, real OAuth expiry/revocation, or conservation of the separate 18-wallet production reference. The later Notion correction has its own local tests and requires a tested final candidate.
